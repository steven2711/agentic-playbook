# Architecture enforcement, deterministic CI, and strict ratcheting

Inventory canonical commands for formatting, lint, type checking, build, unit and integration tests, architecture and API contracts, and security and dependencies. Document setup and pin relevant inputs so local and CI runs use equivalent rules. Use the existing stack’s tools to enforce justified module boundaries, dependency direction, and interfaces. Where a rule needs judgment that tools cannot express, review each change against the engineering conventions for its paths, and promote recurring violations into deterministic checks. Evaluate meaningful changed-code testing and coverage as functionality appears. Turn on the strictest checks the stack offers that are cheap and rarely wrong, such as strict type checking, type-aware lint and rejection of focused or skipped tests, before anything costlier. Add costlier checks only when the repository's shape or a recurring defect justifies them, and state the failure each check prevents. Run the fast checks on changed files where the agent works, before CI.

Classify each check as passed, failed, not applicable with a reason, or unverified with a reason. Require a stable CI gate that fails when an applicable check fails, is skipped, or lacks a result. Verify actual required-check and protection settings before claiming enforcement. Cover secret handling, least privilege, controlled merging, and reproducible setup.

Start applicable clean rules with zero violations. For eligible legacy debt, use reviewed, versioned baselines with stable violation identities, scope, and rationale. Compare the candidate to the trusted baseline and fail any new identity even if another violation was removed and the total stays flat. An identity may be as coarse as file and rule, as tools' native baselines record it; build finer tracking only where a tool already provides it. Remove resolved identities as part of accepting the fix. Reject reintroduction. Treat inline suppressions as baseline entries: each names the rule it silences and gives a reason, and their number cannot grow without review. Security-critical rules prohibit grandfathering. Require independent review of enforcement, baseline, and exception changes. Ensure the candidate cannot pass by changing the policy or baseline that judges it.

During assessment, inspect current guardrails and propose evidence gaps and how to close them. During approved execution, verify an ordinary clean run and isolated negative cases for a prohibited architecture change, failed and skipped checks, equal-count replacement, a returning violation, and unauthorized policy relaxation where applicable. Use temporary fixtures or an isolated checkout and capture expected and actual verdicts. Record missing access or external enforcement as unverified.
