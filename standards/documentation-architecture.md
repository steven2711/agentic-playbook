# Documentation architecture and Claude Code context

Use a concise root `CLAUDE.md` as Claude Code’s authoritative navigation and instruction entry point. Keep the project purpose, essential commands, universally applicable constraints, and links there. Review the actual loading behavior of existing rules, skills, hooks, and settings. Scope guidance to applicable paths where useful, use project skills for repeatable workflows, and link to task-specific documentation. Give each instruction one authoritative home. Inspect existing `AGENTS.md` guidance. Introduce cross-agent instructions only when requested.

Inventory documents by location, purpose, audience, scope, authority, owner, dependencies, issue, and disposition. Consider product requirements and approved acceptance criteria, architecture and dependency direction, ADRs, engineering conventions and verification, domain rules, interfaces and integrations, and deployment and operations. Create each category when current work justifies it. Establish who maintains it, when a change requires an update, how agents discover it, and how it can be verified.

Distinguish approved requirements, architectural contracts, implementation facts, historical decisions, active plans, operational procedures, generated references, and examples. Cite paths, symbols, and lines when sampling claims against implementation, tests, or configuration. Link important contracts to their supporting sources where practical. Report discrepancies and their impact. Escalate unresolved questions of intent before treating implementation or documentation as the governing contract.

Use lightweight deterministic CI checks for applicable links, required files, metadata, generated references, and verifiable paths or command references. Report potential semantic contradictions for evidence-based inspection. Evaluate whether agents can find requirements, decisions, boundaries, and verification commands, and flag ambiguity. Track navigation failures, repeated misunderstandings, and stale-documentation findings where meaningful. See [agent evaluations](agent-evaluations.md).

## Engineering conventions

Give each deployable app or layer, such as web, API, worker, or shared packages, an engineering conventions file scoped to the paths it governs, so it loads only where it applies. A path-scoped `.claude/rules/<app>.md` or a nested `<app>/CLAUDE.md` works. A single-app repository needs one, and its root `CLAUDE.md` or `AGENTS.md` can be that home while the rules fit there. Record only judgment rules that deterministic checks cannot express: layering intent, error-handling and data-access patterns, state management, API design, naming that carries domain meaning, and testing approach. State each rule with its rationale and a short example. Link rules that tooling already enforces instead of restating them. When a convention becomes mechanically checkable, promote it into a deterministic check and remove the prose. Review changes to conventions like enforcement changes. Base recommended conventions on cited public sources, such as the [conventions baseline library](../reference/conventions/README.md), and adopt them only with human approval. Start from the [conventions template](../templates/conventions.md).
